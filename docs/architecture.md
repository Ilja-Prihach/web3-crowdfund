# Архитектура

Проект состоит из двух независимых приложений:

1. `contracts/` содержит правила смарт-контрактов, а блокчейн является источником истины для средств и состояния кампаний.
2. `frontend/` читает данные контракта и предлагает кошельку пользователя подписать транзакции.

Frontend никогда не получает и не хранит приватные ключи пользователей. V2 находится в `main` и развёрнут в Sepolia по отдельному от V1 адресу, см. [`deployments.md`](deployments.md).

## Frontend shell и дизайн-система

Frontend использует Next.js App Router. Корневой layout подключает локально выдаваемые через `next/font` шрифты Manrope и PT Serif, skip-link, общий `AppHeader` и `AppFooter`. Маршрутные страницы передают содержимое внутрь этого shell и сохраняют семантический `main`. `AppHeader` остаётся серверным компонентом. Клиентские части shell — `MobileMenu`, который до 960 px заменяет навигацию кнопкой-бургером с выпадающей панелью и закрывается по Escape или выбору пункта, и компоненты кошелька из Web3-слоя ниже.

Глобальный слой содержит reset, семантические CSS custom properties, базовую типографику, focus-правила и поддержку `prefers-reduced-motion`. Компонентные стили изолированы через SCSS Modules. Общие UI-примитивы `Button`, `Field`, `Skeleton`, `EmptyState` и `ErrorState` находятся в `frontend/src/shared/ui`, а крупные части shell — в `frontend/src/widgets`.

Светлая и тёмная темы используют одни семантические токены. `frontend/src/features/theme/model/theme.ts` хранит допустимые значения, ключ `localStorage` и pre-hydration script; `ThemeToggle` подписывается на системную тему через `useSyncExternalStore`, синхронизирует desktop/mobile экземпляры и сохраняет явный выбор. Корневой layout применяет `data-theme` до отрисовки интерфейса; без JavaScript CSS fallback следует `prefers-color-scheme`. Тёмная тема использует нейтральное направление «Ночной журнал», а изображения остаются исходными без CSS-инверсии. Причины зафиксированы в [`DECISIONS.md#frontend-theme-follows-system-and-persists-choice`](DECISIONS.md#frontend-theme-follows-system-and-persists-choice).

Масштабируемая геометрия интерфейса задаётся преимущественно в `rem`; точные линии, focus outline и responsive breakpoints — в `px`. Подробные причины и правила находятся в [`DECISIONS.md#frontend-styles-are-colocated-scss-modules`](DECISIONS.md#frontend-styles-are-colocated-scss-modules).

Главная страница собирается из независимых widgets `HeroSection`, `HowItWorksSection`, `FundingModesSection`, `TrustSection` и `ProjectStatusSection`. Они следуют карточному направлению из [`DECISIONS.md#frontend-uses-card-surfaces`](DECISIONS.md#frontend-uses-card-surfaces): заголовки секций строит общий `SectionHeader`, а CTA-ссылки — `ButtonLink`, разделяющий классы с `Button`. Семь декоративных сцен лежат как оптимизированные WebP в `assets/` соответствующих widgets и подключаются через `next/image`, см. [`DECISIONS.md#frontend-illustrations-use-raster-exports`](DECISIONS.md#frontend-illustrations-use-raster-exports). Страница последовательно объясняет назначение продукта, движение ETH через контракт, режимы V2, границу доверия и текущую готовность интерфейса без фиктивных кампаний и неподключённых действий. CTA ведут только к существующим якорям, исходному коду и верифицированному контракту в Etherscan.

## Web3-слой frontend

Сеть, адрес V2 и ссылка на контракт в Etherscan заданы один раз в `frontend/src/shared/config/web3.ts`; сеть берётся из `viem/chains` (`sepolia`, chain ID `11155111`). ABI хранится в `frontend/src/shared/config/crowdfundingAbi.ts` как `as const`-модуль. Его генерирует `npm run abi:export` из артефакта `forge build` (`contracts/out/` в Git не попадает), поэтому вручную файл не редактируется.

`getWagmiConfig()` в `frontend/src/shared/config/wagmi.ts` создаёт конфиг wagmi: только Sepolia, HTTP-транспорт на `NEXT_PUBLIC_SEPOLIA_RPC_URL` или публичный RPC viem, коннектор `injected` с обнаружением кошельков по EIP-6963, `ssr: true` и cookie-хранилище. Клиентский `frontend/src/app/providers.tsx` оборачивает shell в `WagmiProvider` и `QueryClientProvider`. Корневой layout читает cookie запроса через `cookieToInitialState` и передаёт состояние подключения провайдеру, поэтому сервер сразу рендерит адрес подключённого кошелька; из-за чтения `headers()` страницы рендерятся динамически, см. [`DECISIONS.md#frontend-wallet-state-hydrates-from-cookie`](DECISIONS.md#frontend-wallet-state-hydrates-from-cookie).

Кошелёк живёт в `frontend/src/features/wallet`:

- `ui/ConnectWallet` — кнопка и модальный `<dialog>` со списком браузерных кошельков; при известном адресе вместо кнопки показывает `WalletMenu`, а то же окно служит для смены кошелька: новый подключается первым, прежний отключается только после успеха, поэтому отмена смены оставляет текущий кошелёк;
- `ui/WalletMenu` — адрес с аватаром из адреса, кошелёк, через который выполнено подключение, полный адрес, копирование, ссылка на Etherscan, смена кошелька и отключение;
- `ui/NetworkBadge` — бейдж сети в шапке: Sepolia или «Другая сеть»;
- `ui/WrongNetworkBanner` — полоса под шапкой с переключением на Sepolia, пока кошелёк в другой сети;
- `model/useWalletNetwork` — единственное место, где вычисляется «кошелёк подключён» и «сеть неверная»; будущие финансовые действия блокируются по этому же хуку;
- `lib/walletErrors` — перевод ошибок кошелька в русский текст по коду или имени во всей цепочке `cause`;
- `lib/walletName` — человекочитаемое имя коннектора, общее для окна и меню.

Подключённым считается кошелёк с известным адресом: и в статусе `connected`, и в статусе `reconnecting`, в котором wagmi восстанавливает сессию из cookie, см. [`gotchas.md#wagmi-restored-session-is-reconnecting`](gotchas.md#wagmi-restored-session-is-reconnecting). Сокращение адреса и оттенок аватара — чистые функции в `frontend/src/shared/lib/address.ts`; регистр EIP-55 при показе не меняется.

## Контракт Crowdfunding

Контракт `Crowdfunding` хранит кампании в `mapping`, где ключ — уникальный числовой идентификатор. Счётчик `nextCampaignId` выдаёт следующий свободный ID.

Каждая `Campaign` содержит:

- адрес создателя;
- режим финансирования `FundingMode`;
- название и описание;
- цель сбора в wei;
- дедлайн в формате Unix timestamp;
- текущую сумму ETH, закреплённую за кампанией;
- признаки вывода средств и отмены.

`FundingMode` имеет два значения:

- `FixedDeadline` (`0`) — кампания ограничена сроком;
- `OpenEnded` (`1`) — кампания работает без дедлайна до достижения цели или отмены.

## Создание кампании

Пользователь вызывает:

```solidity
createCampaign(title, description, goal, fundingMode, durationInDays)
```

Контракт записывает `msg.sender` как creator. Название и описание не могут быть пустыми и ограничены 100 и 1000 UTF-8-байтами соответственно. Цель должна быть больше нуля.

Для `FixedDeadline` длительность должна составлять от 1 до `MAX_DURATION_DAYS`, равного 365. Дедлайн вычисляется как `block.timestamp + durationInDays * 1 days`.

Для `OpenEnded` параметр `durationInDays` обязан быть равен нулю, а сохранённый `deadline` равен нулю. Ненулевой срок отклоняется ошибкой `OpenEndedCampaignMustNotHaveDuration`.

## Изменение дедлайна

Создатель fixed-кампании может вызвать `updateCampaignDeadline(campaignId, durationInDays)`. Новый дедлайн отсчитывается от времени этой транзакции, а не от старого дедлайна.

Изменение разрешено только если:

- кампания существует и не отменена;
- вызов делает creator;
- режим равен `FixedDeadline`;
- кампания ещё не завершилась по времени;
- `totalRaised` равен нулю, то есть первого пожертвования ещё не было;
- новая длительность находится в диапазоне от 1 до 365 дней.

Успешное изменение публикует `CampaignDeadlineUpdated` со старым и новым дедлайном. После первого пожертвования условия кампании больше нельзя менять.

## Пожертвование и достижение цели

Пользователь вызывает `donate(campaignId)` и прикладывает ETH. Контракт увеличивает `totalRaised` кампании и личный вклад в `contributions[campaignId][donor]`.

Пожертвование отклоняется, если кампания не существует, отменена, уже достигла цели, получила нулевую сумму или завершилась по дедлайну в fixed-режиме. У open-ended-кампании проверка времени отсутствует.

Пожертвование, которое первым достигает цели, может превысить оставшуюся сумму и принимается полностью. После него статус немедленно становится `Successful`, а последующие пожертвования запрещены. Автоматический возврат превышения не выполняется.

## Отмена кампании

Creator может вызвать `cancelCampaign(campaignId)`, пока цель не достигнута. Fixed-кампанию нельзя отменить после дедлайна; open-ended-кампания не ограничена временем.

После отмены новые пожертвования и вывод creator запрещены, а участники самостоятельно возвращают активные вклады через `refund`. Повторная отмена запрещена. Успешную кампанию отменить нельзя.

## Вывод средств

Creator может вызвать `withdrawFunds(campaignId)` сразу после достижения цели: ждать дедлайна в любом режиме не нужно. Вывод отклоняется для несуществующей или отменённой кампании, постороннего пользователя, недостигнутой цели или повторной попытки.

Перед переводом ETH контракт устанавливает `fundsWithdrawn` в `true` и публикует `FundsWithdrawn`, затем отправляет всю `totalRaised` creator через `call`. Порядок checks-effects-interactions и `nonReentrant` защищают от повторного вывода. Если перевод не удался, вся транзакция откатывается вместе с флагом и событием.

## Возврат средств

Контракт хранит активный вклад каждого участника во вложенном `mapping` `contributions`.

Возврат доступен:

- после провала `FixedDeadline`, если дедлайн наступил раньше достижения цели;
- сразу после отмены кампании любого режима;
- в любой момент активной `OpenEnded`, пока цель не достигнута.

Возврат запрещён после достижения цели и для адреса без активного вклада. Перед внешним переводом контракт обнуляет вклад участника и уменьшает `campaign.totalRaised` на ту же сумму. Поэтому `totalRaised` означает текущую сумму ETH, закреплённую за кампанией, а не историческую сумму всех пожертвований.

Изменения состояния, событие `RefundClaimed` и перевод ETH выполняются в одной транзакции. При неудачном переводе всё откатывается.

## Статус кампании

`CampaignStatus` не хранится отдельно, а вычисляется функцией `getCampaignStatus` из фактов кампании. Приоритет проверок следующий:

1. `Cancelled` (`4`) — creator отменил кампанию;
2. `Withdrawn` (`3`) — creator вывел средства;
3. `Successful` (`1`) — `totalRaised >= goal`;
4. `Active` (`0`) — open-ended-кампания либо fixed-кампания до дедлайна;
5. `Failed` (`2`) — fixed-кампания достигла дедлайна без цели.

Таким образом, успех наступает непосредственно в транзакции достижения цели. На границе `block.timestamp == deadline` fixed-кампания уже завершена: если цель не достигнута, её статус равен `Failed`.

## События

Контракт публикует события:

- `CampaignCreated`;
- `CampaignDeadlineUpdated`;
- `CampaignCancelled`;
- `DonationMade`;
- `FundsWithdrawn`;
- `RefundClaimed`.

События предназначены для frontend, истории операций и будущего indexer. Бизнес-правила не зависят от событий: источником истины остаётся состояние блокчейна.

`CampaignCreated` пока содержит `campaignId`, creator, цель и вычисленный дедлайн. Режим читается из сохранённой структуры кампании.

## Обработка ошибок

Контракт использует custom errors вместо строковых сообщений в `require`. Это уменьшает revert data и позволяет тестам проверять конкретную причину отката через селектор ошибки.

Вызов `revert` прекращает выполнение и отменяет все изменения состояния текущей транзакции, включая уже опубликованные в её ходе события.

## Получение списка кампаний

Поскольку `mapping` нельзя перебрать, контракт предоставляет `getCampaigns(offset, limit)`.

`offset` указывает ID первой кампании, а `limit` — максимальное число элементов. Ответ содержит массив `CampaignView`: ID, полную `Campaign` и вычисленный статус.

Размер страницы должен быть от 1 до `MAX_PAGE_SIZE`, равного 20. Если `offset` находится за концом списка, возвращается пустой массив; последняя страница может быть короче `limit`.

Frontend вызывает функцию через `eth_call`, поэтому пользователь не подписывает транзакцию и не платит gas. Ограничение страницы всё равно необходимо, поскольку выполнение и ABI-ответ расходуют ресурсы RPC-узла.

# Архитектура

Проект состоит из двух независимых приложений:

1. `contracts/` содержит правила смарт-контрактов, а блокчейн является источником истины для средств и состояния кампаний.
2. `frontend/` читает данные контракта и предлагает кошельку пользователя подписать транзакции.

Frontend никогда не получает и не хранит приватные ключи пользователей. V2 находится в `main` и развёрнут в Sepolia по отдельному от V1 адресу, см. [`deployments.md`](deployments.md).

## Frontend shell и дизайн-система

Frontend использует Next.js App Router. Корневой layout подключает локально выдаваемые через `next/font` шрифты Manrope и PT Serif, skip-link, общий `AppHeader` и `AppFooter`. Маршрутные страницы передают содержимое внутрь этого shell и сохраняют семантический `main`. `AppHeader` остаётся серверным компонентом. Клиентские части shell — `MobileMenu`, который до 1280 px заменяет навигацию кнопкой-бургером с выпадающей панелью и закрывается по Escape или выбору пункта, и компоненты кошелька из Web3-слоя ниже.

Глобальный слой содержит reset, семантические CSS custom properties, базовую типографику, focus-правила и поддержку `prefers-reduced-motion`. Компонентные стили изолированы через SCSS Modules. Общие UI-примитивы `Button`, `Field`, `Skeleton`, `EmptyState` и `ErrorState` находятся в `frontend/src/shared/ui`, а крупные части shell — в `frontend/src/widgets`.

Светлая и тёмная темы используют одни семантические токены. `frontend/src/features/theme/model/theme.ts` хранит допустимые значения, ключ `localStorage` и pre-hydration script; `ThemeToggle` подписывается на системную тему через `useSyncExternalStore`, синхронизирует desktop/mobile экземпляры и сохраняет явный выбор. Корневой layout применяет `data-theme` до отрисовки интерфейса; без JavaScript CSS fallback следует `prefers-color-scheme`. Тёмная тема использует нейтральное направление «Ночной журнал», а изображения остаются исходными без CSS-инверсии. Причины зафиксированы в [`DECISIONS.md#frontend-theme-follows-system-and-persists-choice`](DECISIONS.md#frontend-theme-follows-system-and-persists-choice).

Масштабируемая геометрия интерфейса задаётся преимущественно в `rem`; точные линии, focus outline и responsive breakpoints — в `px`. Подробные причины и правила находятся в [`DECISIONS.md#frontend-styles-are-colocated-scss-modules`](DECISIONS.md#frontend-styles-are-colocated-scss-modules).

Главная страница собирается из независимых widgets `HeroSection`, `HowItWorksSection`, `FundingModesSection`, `TrustSection` и `ProjectStatusSection`. Они следуют карточному направлению из [`DECISIONS.md#frontend-uses-card-surfaces`](DECISIONS.md#frontend-uses-card-surfaces): заголовки секций строит общий `SectionHeader`, а CTA-ссылки — `ButtonLink`, разделяющий классы с `Button`. Семь декоративных сцен лежат как оптимизированные WebP в `assets/` соответствующих widgets и подключаются через `next/image`, см. [`DECISIONS.md#frontend-illustrations-use-raster-exports`](DECISIONS.md#frontend-illustrations-use-raster-exports). Страница последовательно объясняет назначение продукта, движение ETH через контракт, режимы V2, границу доверия и текущую готовность интерфейса без фиктивных кампаний и неподключённых действий. CTA ведут только к существующим якорям, исходному коду и верифицированному контракту в Etherscan.

## Web3-слой frontend

Сеть, адрес V2 и ссылка на контракт в Etherscan заданы один раз в `frontend/src/shared/config/web3.ts`; сеть берётся из `viem/chains` (`sepolia`, chain ID `11155111`). ABI хранится в `frontend/src/shared/config/crowdfundingAbi.ts` как `as const`-модуль. Его генерирует `npm run abi:export` из артефакта `forge build` (`contracts/out/` в Git не попадает), поэтому вручную файл не редактируется.

`getWagmiConfig()` в `frontend/src/shared/config/wagmi.ts` создаёт конфиг wagmi: только Sepolia, HTTP-транспорт на `NEXT_PUBLIC_SEPOLIA_RPC_URL` или публичный узел `ethereum-sepolia-rpc.publicnode.com`, коннектор `injected` с обнаружением кошельков по EIP-6963, `ssr: true` и cookie-хранилище. Клиентский `frontend/src/app/providers.tsx` оборачивает shell в `WagmiProvider` и `QueryClientProvider`. Корневой layout читает cookie запроса через `cookieToInitialState` и передаёт состояние подключения провайдеру, поэтому сервер сразу рендерит адрес подключённого кошелька; из-за чтения `headers()` страницы рендерятся динамически, см. [`DECISIONS.md#frontend-wallet-state-hydrates-from-cookie`](DECISIONS.md#frontend-wallet-state-hydrates-from-cookie).

Кошелёк живёт в `frontend/src/features/wallet`:

- `ui/ConnectWallet` — кнопка и модальный `<dialog>` со списком браузерных кошельков; при известном адресе вместо кнопки показывает `WalletMenu`, а то же окно служит для смены кошелька: новый подключается первым, прежний отключается только после успеха, поэтому отмена смены оставляет текущий кошелёк;
- `ui/WalletMenu` — адрес с аватаром из адреса, кошелёк, через который выполнено подключение, полный адрес, копирование, ссылка на Etherscan, смена кошелька и отключение;
- `ui/NetworkBadge` — бейдж сети в шапке: Sepolia или «Другая сеть»;
- `ui/WrongNetworkBanner` — полоса под шапкой с переключением на Sepolia, пока кошелёк в другой сети;
- `model/useWalletNetwork` — единственное место, где вычисляется «кошелёк подключён» и «сеть неверная»; будущие финансовые действия блокируются по этому же хуку;
- `lib/walletErrors` — перевод ошибок кошелька в русский текст по коду или имени во всей цепочке `cause`;
- `lib/walletName` — человекочитаемое имя коннектора, общее для окна и меню.

Подключённым считается кошелёк с известным адресом: и в статусе `connected`, и в статусе `reconnecting`, в котором wagmi восстанавливает сессию из cookie, см. [`gotchas.md#wagmi-restored-session-is-reconnecting`](gotchas.md#wagmi-restored-session-is-reconnecting). Сокращение адреса и оттенок аватара — чистые функции в `frontend/src/shared/lib/address.ts`; регистр EIP-55 при показе не меняется.

## On-chain-каталог frontend

Маршрут `/campaigns` (`frontend/src/app/campaigns/page.tsx`) рендерит клиентский виджет `widgets/CampaignCatalog`. Данные читаются напрямую из V2 без кошелька, см. [`DECISIONS.md#frontend-reads-sepolia-directly`](DECISIONS.md#frontend-reads-sepolia-directly).

Сущность кампании живёт в `frontend/src/entities/campaign`:

- `model/useCampaignCatalog` делает два зависимых `useReadContract`: `nextCampaignId`, затем `getCampaigns(offset, limit)`. Оба запроса явно указывают `chainId` Sepolia. Второй запрос выключен (`enabled: false`), пока неизвестно окно страницы, поэтому при нуле кампаний он не отправляется. Выключенный запрос в TanStack Query v5 имеет статус `pending`, поэтому загрузка считается только для запроса, который действительно должен выполниться;
- `model/campaign` переводит ответ контракта в модель: индексы enum `CampaignStatus` и `FundingMode` становятся строковыми ключами (`"active"`, `"openEnded"`) с подписями, тип сырого ответа выводится из ABI через `ContractFunctionReturnType`. Неизвестный индекс бросает ошибку внутри `select`, и каталог показывает состояние ошибки вместо неверного статуса. Порядок массивов обязан совпадать с порядком enum в `Crowdfunding.sol`: ABI хранит enum как `uint8`, и TypeScript расхождение не заметит;
- `lib/pagination` вычисляет окно `offset/limit`. `getCampaigns` читает по возрастанию ID, поэтому для порядка «сначала новые» окно отсчитывается с конца, а результат разворачивается. `limit` последней страницы точный: при `limit = 20` контракт вернул бы уже показанные ID;
- `lib/money` форматирует wei без перевода в `number`: строка из `formatEther` передаётся в `Intl.NumberFormat`, лишние знаки отбрасываются (`roundingMode: "trunc"`), а суммы меньше 0,0001 ETH показываются по значащим цифрам. Процент считается в `bigint` и округляется вниз, поэтому 100% появляется только при `totalRaised >= goal`, как в контракте;
- `lib/deadline` переводит Unix-дедлайн в «N дней» или «N ч»; время фиксируется при открытии страницы;
- `CampaignCard`, `CampaignStatus`, `CampaignProgress` и `CampaignArtwork` — карточка одинакового размера с бейджем статуса, меткой срока, прогрессом, подсказкой о судьбе средств и автором. Ссылка на страницу кампании стоит на заголовке и растягивается на всю карточку через `::after`, поэтому в дереве доступности карточка остаётся одной ссылкой. Обложка — demo-иллюстрация для кампаний проекта или детерминированный узор по ID, см. [`DECISIONS.md#frontend-demo-campaigns-use-off-chain-covers`](DECISIONS.md#frontend-demo-campaigns-use-off-chain-covers).

Фильтры «Идёт сбор / Завершены» и по типу сбора работают только по загруженной странице из не более чем 20 кампаний; при нескольких страницах интерфейс говорит об этом явно. Тип сбора и сортировка выбираются через `shared/ui/Select` — собственный выпадающий список с ролью `combobox`, навигацией стрелками, `Home`/`End`, `Escape` и закрытием по клику снаружи; переход между пунктами вынесен в чистую `selectNavigation` с unit-тестом. Каталог различает загрузку, пустой контракт, ошибку RPC с повтором и пустой результат фильтров.

Модули, которые загружают unit-тесты, импортируют соседей относительным путём с `.ts`: `node --test` не понимает псевдоним `@/`, см. [`gotchas.md#node-test-does-not-resolve-path-alias`](gotchas.md#node-test-does-not-resolve-path-alias). Для литералов `bigint` в `frontend/tsconfig.json` установлен `target: ES2020`; код для браузера собирает Next.js, а `tsc` только проверяет типы.

## Страница кампании frontend

Маршрут `/campaigns/[id]` (`frontend/src/app/campaigns/[id]/page.tsx`) получает `params` промисом, проверяет ID через `entities/campaign/lib/campaignId` и передаёт результат клиентскому виджету `widgets/CampaignDetails`. `parseCampaignId` принимает только десятичные цифры без ведущих нулей в пределах `uint256`: пустая строка, `0x1`, `1e3` и `007` отклоняются до `BigInt`, который понял бы их по-своему, а у каждой кампании остаётся один URL.

`model/useCampaign` читает кампанию вызовом `getCampaigns(id, 1)`: один запрос возвращает кампанию вместе со статусом, посчитанным контрактом, переиспользует `toCampaign`, а пустой массив означает, что кампании нет. Автогеттер `campaigns(id)` не используется: он возвращает кортеж без статуса и нули для несуществующего ID. Вклад подключённого кошелька читается автогеттером `contributions(id, address)` только при известных кошельке и кампании; неизвестный вклад показывается как неизвестный, а не как ноль. Общие адрес, ABI и `chainId` чтения лежат в `model/contract`.

Виджет различает неверный адрес (без запроса в сеть), отсутствующую кампанию, загрузку и ошибку RPC с повтором. На странице показаны обложка, статус, срок, режим, название, создатель со ссылкой на Etherscan, полное on-chain-описание, панель сбора и правила режима. На mobile панель сбора идёт сразу после шапки, а описание — после неё; на desktop панель закреплена справа (`grid-template-areas`).

`lib/actions` вычисляет доступные действия по revert-условиям контракта: поддержать — активная кампания; вывести — создатель успешной; отменить — создатель активной; изменить срок — создатель активной fixed-кампании без вкладов; вернуть вклад — вклад больше нуля при статусе `failed`, `cancelled` или активной open-ended-кампании. Создатель сравнивается через `isAddressEqual` без учёта регистра. Окончательно решает всегда контракт. Пожертвование описано в следующем разделе, остальные действия — в разделе «Действия с кампанией frontend». Расширенные разделы мокапа — бюджет, план, риски и участники — требуют off-chain-метаданных или indexer и не показываются.

## Пожертвование и жизненный цикл транзакции frontend

Форма `features/campaign-donate/ui/DonateForm` встроена в панель сбора активной кампании. Сумма из поля проходит `shared/lib/ethAmount`: запятая допустима, ноль, мусор и больше 18 знаков после запятой отклоняются до любого запроса в сеть, потому что `parseEther` молча округлил бы лишние знаки. Кнопка выключена без кошелька и в чужой сети по `useWalletNetwork`.

`features/campaign-donate/model/useDonate` выполняет транзакцию в собственной мутации TanStack Query: сначала `simulateContract` прогоняет `donate` через `eth_call` от имени кошелька, затем `writeContract` отправляет ровно проверенный `request`. Revert ловится до окна кошелька и до траты gas. `useWaitForTransactionReceipt` ждёт блок; транзакция, выполненная с revert, приходит ошибкой. После подтверждения все запросы с ключом `readContract` помечаются устаревшими, и страница перечитывает кампанию, вклад и каталог.

Этап вычисляется одним значением: `signing` — ждём подпись, `confirming` — hash есть, блока нет, `confirmed` — receipt успешен, `failed`. Проверка `failed` идёт раньше `confirming`, иначе транзакция с revert навсегда зависла бы в ожидании сети. `features/transaction-status/ui/TransactionStatus` показывает этапы по локальному мокапу UX-состояний: подпись, ожидание с ссылкой на hash, успех, отказ в кошельке, revert с текстом custom error и кнопкой «Обновить кампанию» и нехватку ETH.

`features/transaction-status/lib/transactionErrors` переводит custom errors контракта по имени, декодированному viem из ABI (`ContractFunctionRevertedError.data.errorName`); ключи переводов типизированы `ContractErrorName<typeof crowdfundingAbi>`. Перевод ищется сначала в словаре конкретного действия, затем в общем: одна ошибка означает разное в разных функциях — `GoalWasReached` при вкладе значит «вклады больше не принимаются», при возврате — «вклады больше не возвращаются», при отмене — «успешный сбор отменить нельзя». Хук действия возвращает свой словарь, `TransactionStatus` принимает его в `errorMessages`. Непереведённая ошибка показывается по имени. `isUserRejection` и `isContractRevert` различают отказ (`4001`), revert и остальные сбои; общие ошибки кошелька переводит `getWalletErrorMessage`.

## Создание кампании frontend

Маршрут `/campaigns/new` рендерит клиентский виджет `widgets/CampaignCreate`: описание, режим и цель, проверка и запуск — на одной странице, справа живое превью карточки и вызов `createCampaign(…)` с аргументами, которые уйдут в контракт.

`features/campaign-create/lib/campaignDraft` повторяет проверки `createCampaign` до подписи: название 1–100 и описание 1–1000 **байт UTF-8**, как `bytes(value).length` в Solidity (`shared/lib/utf8`; кириллица занимает 2 байта, эмодзи — 4), цель через `parseEthAmount`, срок `FixedDeadline` — целое число 1–365 дней, а у `OpenEnded` всегда `0`, поэтому `OpenEndedCampaignMustNotHaveDuration` из интерфейса не получить. Тексты обрезаются по краям до подсчёта и отправки. Успешная проверка возвращает готовый кортеж аргументов.

Запись идёт через общий `features/transaction-status/model/useContractTransaction` — тот же путь «симуляция → подпись → receipt → обновление чтений», на котором построен `useDonate`. `useCreateCampaign` берёт ID новой кампании из события `CampaignCreated` в receipt (`parseEventLogs`), а не из `nextCampaignId`: событие относится ровно к этой транзакции, поэтому кампания, созданная кем-то в том же блоке, не подменит ID. После подтверждения страница переходит на `/campaigns/<id>`.

Поля для обложки нет: контракт V2 не хранит изображений, а backend для файлов ещё не создан, см. [`DECISIONS.md#campaign-media-lives-in-backend`](DECISIONS.md#campaign-media-lives-in-backend).

## Действия с кампанией frontend

Под формой вклада `features/campaign-actions/ui/CampaignActions` показывает блок «Управление сбором» с теми действиями, которые `getAvailableActions` разрешил подключённому адресу: вывести средства, вернуть вклад, изменить срок, отменить сбор. Необратимая отмена всегда последняя и перед подписью требует подтверждения в карточке. Кнопки выключены в чужой сети.

`model/useCampaignAction(campaignId, "refund" | "cancelCampaign" | "withdrawFunds")` обслуживает три функции с одинаковой сигнатурой `(uint256 campaignId)`, `model/useUpdateDeadline` — `updateCampaignDeadline(campaignId, days)`. Оба построены на `useContractTransaction` и проходят симуляцию перед подписью. Сумма вывода или возврата запоминается при отправке: после подтверждения контракт её обнуляет, а статус должен показать, сколько ушло.

Правило срока «целое число дней от 1 до 365» лежит в `entities/campaign/lib/duration`, его используют и создание, и смена срока: одна feature не импортирует другую. Новый срок контракт отсчитывает от блока подтверждения (`block.timestamp + days`), а не от прежнего дедлайна, поэтому форма предупреждает, что срок может и сократиться, и показывает примерную дату.

## Backend

Backend — отдельное приложение `backend/` на Node.js, TypeScript и Fastify, см. [`DECISIONS.md#backend-uses-fastify-on-node`](DECISIONS.md#backend-uses-fastify-on-node). Сейчас реализованы каркас, подключение к PostgreSQL и модуль `chain`: `app.ts` собирает приложение, `server.ts` открывает порт. Разделение нужно тестам: они вызывают `buildApp()` и отправляют запросы через `app.inject()` в памяти, без сети.

`config/env.ts` читает переменные окружения в одном месте и проверяет их при старте: неверный `PORT`, `LOG_LEVEL`, `DATABASE_URL` или `SEPOLIA_RPC_URL` останавливает процесс сразу; значения строк подключения в текст ошибки не попадают. По умолчанию сервер слушает только `127.0.0.1`. На `SIGINT` и `SIGTERM` вызывается `app.close()`: новые запросы не принимаются, текущие завершаются.

`shared/errors.ts` отвечает на любую ошибку в формате `{ "error": { "code", "message" } }`: `code` — стабильный машинный ключ для клиента, `message` — пояснение для разработчика. Ошибки `4xx` передают свой статус и код; текст ошибок `5xx` пишется только в лог, а клиент получает `INTERNAL_ERROR`, чтобы наружу не утекли SQL, пути или секреты. Неизвестный маршрут отвечает `404 NOT_FOUND`.

`db/client.ts` создаёт пул `pg.Pool` до 10 соединений и клиент Drizzle поверх него; пул создаёт и закрывает `server.ts` в хуке `onClose`, то есть последним шагом плавной остановки. У пула обязателен слушатель `error`: без него обрыв простаивающего соединения при перезапуске базы роняет процесс, см. [`gotchas.md#pg-pool-idle-error-crashes-process`](gotchas.md#pg-pool-idle-error-crashes-process). Схема таблиц — `db/schema.ts`, SQL-миграции генерирует `drizzle-kit` в `backend/drizzle/`.

Первая миграция создаёт хранилище indexer:

- `chain_events` — журнал сырых событий контракта: сеть, адрес контракта, блок, транзакция, номер лога, имя события, `campaign_id` и остальные аргументы в `jsonb`. Первичный ключ `(chain_id, tx_hash, log_index)` не даёт записать одно событие дважды. Индекс `(chain_id, contract_address, block_number, log_index)` задаёт порядок воспроизведения для проекций;
- `indexer_checkpoints` — последний полностью обработанный `finalized`-блок с ключом `(chain_id, contract_address)`, поэтому позиция одной сети или контракта не может принадлежать другим.

Значения `uint256` — ID кампаний, а в проекциях и суммы в wei — хранятся как `NUMERIC(78, 0)` и читаются в JavaScript как `bigint`: PostgreSQL `bigint` вмещает только около 9,2 ETH в wei. Внутри `jsonb` большие числа и адреса лежат строками, потому что в JSON нет `bigint`. Формат адресов и хэшей (строчные `0x…`), допустимые имена событий и положительный chain ID проверяет сама база через `CHECK`, а не только код. Хэш блока не хранится: indexer читает только `finalized`-блоки, см. [`DECISIONS.md#indexer-reads-finalized-logs`](DECISIONS.md#indexer-reads-finalized-logs). Запись событий и сдвиг checkpoint появятся вместе с чтением логов.

`chain/` описывает контракт V2 для backend. `contract.ts` хранит сеть Sepolia из `viem/chains`, адрес, блок deploy `12014545` и ABI. Адрес и блок сверяются тестом с [`deployments.md`](deployments.md), а `crowdfundingAddressInDatabase` даёт адрес в нижнем регистре, как требует `CHECK` таблицы `chain_events`. `crowdfundingAbi.ts` генерирует `npm run abi:export` из той же сборки Foundry, что и frontend; тест сравнивает две копии ABI, и забытая перегенерация одной из них роняет CI. Типы аргументов событий viem выводит из `as const`-ABI, поэтому опечатка в имени поля ловится `npm run typecheck`. `client.ts` создаёт клиент чтения viem из `SEPOLIA_RPC_URL`: клиент передаётся зависимостью, а URL, который может содержать ключ провайдера, не логируется. Первыми клиент подключат indexer (#54) и вход подписью (#52); узел с историей событий для indexer выбирается в #71, см. [`gotchas.md#public-rpc-prunes-log-history`](gotchas.md#public-rpc-prunes-log-history).

Вторая миграция создаёт таблицы входа подписью:

- `auth_nonces` — одноразовые nonce SIWE со сроком. Первичный ключ по nonce не даёт выдать один nonce дважды, индекс по `expires_at` нужен для попутной чистки и подсчёта живых nonce;
- `auth_sessions` — серверные сессии: SHA-256 идентификатора из cookie, адрес в нижнем регистре, время создания и срок. Сам идентификатор в базе не хранится, поэтому дамп таблицы не даёт готовых cookie. Для случайных 32 байт быстрого хэша достаточно: перебор невозможен, соль и медленный хэш нужны только паролям.

Маршруты описываются схемами TypeBox, подключёнными через type provider в `buildApp`: одна схема и проверяет данные, и задаёт тип TypeScript, а ответ сериализуется только по описанным полям. Формат ошибки `ApiError` тоже выводится из схемы `ApiErrorSchema`.

Модуль `modules/auth` — вход подписью EIP-4361, разложенный по слоям: `routes.ts` (HTTP, cookie, коды ответа, лимиты), `service.ts` (правила проверки), `session.ts` (чтение сессии и хук `requireSession`), `repository.ts` (SQL), `schemas.ts` (TypeBox). Маршруты регистрируются под префиксом `/v1/auth`.

- `POST /v1/auth/nonce` → `201 { nonce }` с `Cache-Control: no-store`. Nonce — 32 байта `crypto.randomBytes` в hex, срок 10 минут по часам базы (`now() + interval '10 minutes'`), просроченные nonce удаляются попутно при каждой выдаче.
- `POST /v1/auth/verify { message, signature }` проверяет от дешёвого к дорогому: схема тела (`400`), поля сообщения, nonce, подпись. `validateSiweMessage` из viem сверяет `domain` с хостом `APP_ORIGIN`, адрес, `expirationTime` и `notBefore`; остальное viem не проверяет, поэтому сервис сам сверяет `uri` с `APP_ORIGIN`, `scheme`, `chainId` `11155111`, `version` `1` и возраст `issuedAt` (не старше 10 минут, не позже чем через минуту). Затем nonce гасится через `DELETE … RETURNING`, если он выдан и не истёк: один nonce — одна попытка, и запрос с выдуманным, использованным или просроченным nonce не доходит до RPC. Подпись обычного кошелька проверяется локально (`recoverMessageAddress`); только если адрес не совпал — смарт-кошелёк или чужая подпись, — сервис берёт разрешение из бюджета RPC и вызывает `verifyHash` (`eth_call` валидатора ERC-6492). После успешной проверки создаётся сессия на 7 дней по часам базы; просроченные сессии удаляются попутно. Ответ — `200 { address, expiresAt }` и cookie `openfund_session` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 7 дней) со случайными 32 байтами в `base64url`.
- Любой отказ — `401 SIWE_INVALID` без подробностей; причина пишется в лог уровня `info`, текст сообщения и подпись — нет. Упавший RPC обычным кошелькам не мешает, а смарт-кошелёк получает `401`: viem превращает сетевую ошибку проверки в `false`.
- `GET /v1/auth/session` → `200 { address, expiresAt }` с `no-store` или `401 UNAUTHORIZED`. Просроченная сессия считается отсутствующей, даже если строка ещё в базе.
- `POST /v1/auth/logout` удаляет сессию по хэшу и очищает cookie; без cookie и повторно отвечает тем же `204`.
- `requireSession(db)` — preHandler для маршрутов, которым нужен вход (#49, #51): кладёт сессию в `request.session` или отвечает `401`, а подделанную или просроченную cookie очищает. Поле объявлено через `declare module "fastify"` и `decorateRequest`. Атрибуты cookie лежат в одной константе `sessionCookieOptions`: браузер удаляет cookie, только если `path`, `secure` и `sameSite` совпадают с установкой.

Защита маршрутов входа:

- `@fastify/rate-limit` с `global: false` ограничивает запросы с одного адреса в минуту: nonce 10, verify 10, session 60, logout 30; сверх лимита — `429 RATE_LIMITED` с `retry-after`. Адрес — `request.ip`: без `TRUST_PROXY` это адрес соединения, с ним — адрес клиента из `X-Forwarded-For` только от доверенного прокси. Плагин сам считает IPv6 по подсети `/64` (иначе владелец подсети обходил бы лимит перебором адресов) и `::ffff:1.2.3.4` — как `1.2.3.4`, см. [`DECISIONS.md#frontend-and-backend-share-one-origin`](DECISIONS.md#frontend-and-backend-share-one-origin).
- Бюджет проверок подписи через RPC — 30 в минуту на сервер (`shared/fixed-window.ts`); сверх него — `503 AUTH_BUSY` с `retry-after: 60`. Бюджет тратят только подписи, не проверенные локально, поэтому вход обычными кошельками он не блокирует.
- Общего потолка nonce нет: его можно было бы забить запросами с многих адресов и закрыть вход всем (#83). Рост `auth_nonces` ограничивает лимит на адрес — не больше 100 живых nonce на адрес или подсеть `/64` за 10 минут, строки сами уходят при чистке. Не чаще раза в минуту выдача nonce пересчитывает живые строки и при 10 000 и больше пишет в лог `warn` «many live sign-in nonces». Счётчики живут в памяти процесса: при нескольких экземплярах backend им понадобится общее хранилище.
- POST-маршруты сверяют заголовок `Origin` с `APP_ORIGIN`: чужой — `403 ORIGIN_FORBIDDEN`; запрос без `Origin` (не из браузера) пропускается.
- `shared/logger.ts` заменяет заглушкой `headers.cookie`, `headers["set-cookie"]`, `body.message` и `body.signature`. Ключ `req` Fastify и так прогоняет через свой сериализатор, который пишет только метод, URL и адрес; `redact` защищает от прямого лога `request.headers` или `request.body`.

Лимиты задаются `defaultAuthLimits`; тесты уменьшают их через `authLimits` в зависимостях `buildApp`.

Интеграционные тесты работают на стенде Anvil (`src/test/anvil.ts`, `src/test/crowdfunding.ts`, подробности — в [`backend/README.md`](../backend/README.md#стенд-anvil)): локальный узел с chain ID Sepolia, свежий контракт V2 и снимок состояния на каждый тест. На нём проверены все шесть событий V2, разобранные backend-ABI, и вход смарт-кошельком: развёрнутый ERC-1271 и неразвёрнутый ERC-6492 (тестовые контракты `contracts/test/helpers/TestSmartWallet.sol`). viem не знает адреса валидатора ERC-6492 в Sepolia, поэтому проверка идёт «без развёртывания» — `eth_call` с байткодом валидатора — и одинаково работает в Sepolia и на Anvil.

`buildApp` получает `{ db, chain, appOrigin, authLimits? }`: клиент цепочки создаёт `server.ts` из `SEPOLIA_RPC_URL`, а тесты подставляют узел без сети из `test/app.ts`, который отвечает на `eth_call` отказом или имитирует упавший RPC. Тип `ChainClient` — `PublicClient` для Sepolia без привязки к транспорту.

Модуль `modules/health` отвечает на два вопроса. `GET /health` — жив ли процесс; БД не трогает, потому что перезапуск сервера при упавшей базе не помогает. `GET /ready` — готов ли он обслуживать запросы: выполняет `select 1` и при недоступной базе отвечает `503 NOT_READY` без текста ошибки PostgreSQL.

Локальный PostgreSQL 18.4 поднимает `compose.yaml` в корне репозитория. Порт открыт только на `127.0.0.1:5433`; при первом запуске тома скрипт из `backend/db/init/` создаёт отдельную БД `openfund_test` для тестов.

Принятая структура, по которой будет расти код:

```
backend/src/
  server.ts       запуск API
  indexer.ts      запуск indexer — второй процесс
  app.ts          сборка Fastify: плагины, модули, обработчик ошибок
  config/         переменные окружения с проверкой при старте
  db/             клиент Drizzle, схема, миграции
  chain/          клиент viem, ABI, адрес и блок deploy
  modules/<имя>/  routes.ts → service.ts → repository.ts, schemas.ts
  indexer/        чтение логов, обработчики событий, checkpoint
  shared/         ошибки и общие утилиты
```

Внутри модуля зависимости идут только вниз: маршрут разбирает HTTP, сервис применяет правила, репозиторий выполняет запросы к БД. Внешние ресурсы — БД и клиент блокчейна — передаются в `buildApp`, а не импортируются глобально, поэтому тест подставляет свои. Каждый модуль подключается как плагин Fastify со своими маршрутами и хуками.

## Контракт Crowdfunding

Контракт `Crowdfunding` хранит кампании в `mapping`, где ключ — уникальный числовой идентификатор. Счётчик `nextCampaignId` выдаёт следующий свободный ID.

Каждая `Campaign` содержит:

- адрес создателя;
- режим финансирования `FundingMode`;
- название и описание;
- цель сбора в wei;
- дедлайн в формате Unix timestamp;
- текущую сумму ETH, закреплённую за кампанией;
- признаки вывода средств и отмены.

`FundingMode` имеет два значения:

- `FixedDeadline` (`0`) — кампания ограничена сроком;
- `OpenEnded` (`1`) — кампания работает без дедлайна до достижения цели или отмены.

## Создание кампании

Пользователь вызывает:

```solidity
createCampaign(title, description, goal, fundingMode, durationInDays)
```

Контракт записывает `msg.sender` как creator. Название и описание не могут быть пустыми и ограничены 100 и 1000 UTF-8-байтами соответственно. Цель должна быть больше нуля.

Для `FixedDeadline` длительность должна составлять от 1 до `MAX_DURATION_DAYS`, равного 365. Дедлайн вычисляется как `block.timestamp + durationInDays * 1 days`.

Для `OpenEnded` параметр `durationInDays` обязан быть равен нулю, а сохранённый `deadline` равен нулю. Ненулевой срок отклоняется ошибкой `OpenEndedCampaignMustNotHaveDuration`.

## Изменение дедлайна

Создатель fixed-кампании может вызвать `updateCampaignDeadline(campaignId, durationInDays)`. Новый дедлайн отсчитывается от времени этой транзакции, а не от старого дедлайна.

Изменение разрешено только если:

- кампания существует и не отменена;
- вызов делает creator;
- режим равен `FixedDeadline`;
- кампания ещё не завершилась по времени;
- `totalRaised` равен нулю, то есть первого пожертвования ещё не было;
- новая длительность находится в диапазоне от 1 до 365 дней.

Успешное изменение публикует `CampaignDeadlineUpdated` со старым и новым дедлайном. После первого пожертвования условия кампании больше нельзя менять.

## Пожертвование и достижение цели

Пользователь вызывает `donate(campaignId)` и прикладывает ETH. Контракт увеличивает `totalRaised` кампании и личный вклад в `contributions[campaignId][donor]`.

Пожертвование отклоняется, если кампания не существует, отменена, уже достигла цели, получила нулевую сумму или завершилась по дедлайну в fixed-режиме. У open-ended-кампании проверка времени отсутствует.

Пожертвование, которое первым достигает цели, может превысить оставшуюся сумму и принимается полностью. После него статус немедленно становится `Successful`, а последующие пожертвования запрещены. Автоматический возврат превышения не выполняется.

## Отмена кампании

Creator может вызвать `cancelCampaign(campaignId)`, пока цель не достигнута. Fixed-кампанию нельзя отменить после дедлайна; open-ended-кампания не ограничена временем.

После отмены новые пожертвования и вывод creator запрещены, а участники самостоятельно возвращают активные вклады через `refund`. Повторная отмена запрещена. Успешную кампанию отменить нельзя.

## Вывод средств

Creator может вызвать `withdrawFunds(campaignId)` сразу после достижения цели: ждать дедлайна в любом режиме не нужно. Вывод отклоняется для несуществующей или отменённой кампании, постороннего пользователя, недостигнутой цели или повторной попытки.

Перед переводом ETH контракт устанавливает `fundsWithdrawn` в `true` и публикует `FundsWithdrawn`, затем отправляет всю `totalRaised` creator через `call`. Порядок checks-effects-interactions и `nonReentrant` защищают от повторного вывода. Если перевод не удался, вся транзакция откатывается вместе с флагом и событием.

## Возврат средств

Контракт хранит активный вклад каждого участника во вложенном `mapping` `contributions`.

Возврат доступен:

- после провала `FixedDeadline`, если дедлайн наступил раньше достижения цели;
- сразу после отмены кампании любого режима;
- в любой момент активной `OpenEnded`, пока цель не достигнута.

Возврат запрещён после достижения цели и для адреса без активного вклада. Перед внешним переводом контракт обнуляет вклад участника и уменьшает `campaign.totalRaised` на ту же сумму. Поэтому `totalRaised` означает текущую сумму ETH, закреплённую за кампанией, а не историческую сумму всех пожертвований.

Изменения состояния, событие `RefundClaimed` и перевод ETH выполняются в одной транзакции. При неудачном переводе всё откатывается.

## Статус кампании

`CampaignStatus` не хранится отдельно, а вычисляется функцией `getCampaignStatus` из фактов кампании. Приоритет проверок следующий:

1. `Cancelled` (`4`) — creator отменил кампанию;
2. `Withdrawn` (`3`) — creator вывел средства;
3. `Successful` (`1`) — `totalRaised >= goal`;
4. `Active` (`0`) — open-ended-кампания либо fixed-кампания до дедлайна;
5. `Failed` (`2`) — fixed-кампания достигла дедлайна без цели.

Таким образом, успех наступает непосредственно в транзакции достижения цели. На границе `block.timestamp == deadline` fixed-кампания уже завершена: если цель не достигнута, её статус равен `Failed`.

## События

Контракт публикует события:

- `CampaignCreated`;
- `CampaignDeadlineUpdated`;
- `CampaignCancelled`;
- `DonationMade`;
- `FundsWithdrawn`;
- `RefundClaimed`.

События предназначены для frontend, истории операций и будущего indexer. Бизнес-правила не зависят от событий: источником истины остаётся состояние блокчейна.

`CampaignCreated` пока содержит `campaignId`, creator, цель и вычисленный дедлайн. Режим читается из сохранённой структуры кампании.

## Обработка ошибок

Контракт использует custom errors вместо строковых сообщений в `require`. Это уменьшает revert data и позволяет тестам проверять конкретную причину отката через селектор ошибки.

Вызов `revert` прекращает выполнение и отменяет все изменения состояния текущей транзакции, включая уже опубликованные в её ходе события.

## Получение списка кампаний

Поскольку `mapping` нельзя перебрать, контракт предоставляет `getCampaigns(offset, limit)`.

`offset` указывает ID первой кампании, а `limit` — максимальное число элементов. Ответ содержит массив `CampaignView`: ID, полную `Campaign` и вычисленный статус.

Размер страницы должен быть от 1 до `MAX_PAGE_SIZE`, равного 20. Если `offset` находится за концом списка, возвращается пустой массив; последняя страница может быть короче `limit`.

Frontend вызывает функцию через `eth_call`, поэтому пользователь не подписывает транзакцию и не платит gas. Ограничение страницы всё равно необходимо, поскольку выполнение и ABI-ответ расходуют ресурсы RPC-узла.

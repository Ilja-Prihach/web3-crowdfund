# Рабочий процесс

GitHub хранит текущее движение задач, а репозиторий — долгоживущие продуктовые и технические решения. Канонический порядок этапов остаётся в [`roadmap.md`](roadmap.md); [OpenFund Delivery](https://github.com/users/Ilja-Prihach/projects/1) показывает, что происходит с конкретными задачами сейчас.

## Доска

Основное представление `Работа` использует шесть стадий:

1. `Идеи` — результат или границы ещё нужно уточнить;
2. `Готово к работе` — критерии приёмки понятны, зависимостей для старта нет;
3. `В работе` — существует одна активная ветка и назначенный исполнитель;
4. `Проверка` — открыт pull request или идёт приёмка;
5. `Ждёт решения` — продолжение требует решения владельца;
6. `Завершено` — изменение влито, Issue закрыта и документация актуальна.

Представление `Весь план` показывает те же карточки таблицей. Поле `Этап` связывает задачу с крупным направлением roadmap. Порядок карточек в `Готово к работе` задаёт приоритет; отдельного поля приоритета нет.

## От задачи до merge

1. Новая работа начинается с Issue. Для возможности и ошибки используются формы в `.github/ISSUE_TEMPLATE/`.
2. Перед переводом в `Готово к работе` у задачи должны быть проверяемые критерии приёмки и понятные зависимости.
3. Исполнитель назначает себя, переводит карточку в `В работе` и создаёт ветку от актуального `main`: `feat/45-indexer-schema` или `fix/56-refund-state`.
4. Коммиты следуют Conventional Commits на английском. Номер Issue в сообщение коммита не добавляется.
5. Pull request использует шаблон репозитория, содержит `Closes #N`, выполненные проверки и честно перечисляет непроверенное. Визуальное изменение получает снимки 390 и 1440 px.
6. Карточка переходит в `Проверка`. После merge связанная Issue закрывается, а карточка становится `Завершено`.

Если появляется вопрос, который меняет продуктовые границы, безопасность или архитектуру, исполнитель записывает его в Issue и переводит карточку в `Ждёт решения`. После ответа критерии обновляются, и карточка возвращается в `Готово к работе` или `В работе`.

## Готовность и завершение

Задача готова к работе, когда результат сформулирован независимо от реализации, критерии можно проверить, зависимости разрешены, а изменение Solidity при необходимости отдельно одобрено владельцем.

Задача завершена, когда код и подходящие тесты влиты, относящиеся к подсистеме локальные и удалённые проверки зелёные, приёмочные доказательства приложены, документация обновлена, а Issue закрыта через pull request.

Исправление подтверждённого бага начинается с падающего теста или другого воспроизводимого доказательства. Pull request фиксирует исходный красный результат и зелёный результат после исправления.

## Автоматические проверки

Workflow `PR metadata` проверяет название pull request по Conventional Commits, ограничение 72 символа и наличие `Closes #N`, `Fixes #N` или `Resolves #N` в описании. Он перезапускается на каждом новом push в pull request, поэтому вместе с основными CI-workflows входит в обязательные checks защищённой ветки `main`. Основные CI-workflows отменяют устаревший запуск при новом push в тот же pull request, но продолжают выполняться все вместе.

# Текущее состояние проекта

Обновлено: 23 ноября 2026 года. Контрактный этап и Frontend MVP завершены; идёт этап backend/indexer.

## Текущий этап

Контракт V2 с режимами `FixedDeadline` и `OpenEnded` реализован, полностью проверен, влит в `main`, развёрнут и верифицирован в Ethereum Sepolia. Fixed и open-ended сценарии выполнены on-chain через `cast`.

Frontend MVP на Next.js, React и TypeScript завершён десятью PR. PR 1 создал воспроизводимую техническую основу, PR 2 добавил дизайн-систему и application shell, а PR 3 перевёл главную на карточное направление по локальным мокапам: иллюстрированные hero, шаги и режимы, блок доверия со сценой-сейфом, финальный CTA и мобильное меню. PR 4 добавил Web3-основу: wagmi, viem и TanStack Query, сгенерированный ABI, providers с восстановлением сессии из cookie, подключение и смену браузерного кошелька, меню адреса, бейдж сети и переключение на Sepolia. PR 4.1 добавил светлую и тёмную темы с системным начальным значением, сохранением явного выбора и тёмным editorial-направлением «Ночной журнал». PR 5 добавил on-chain-каталог `/campaigns`: чтение `nextCampaignId` и `getCampaigns` без кошелька, карточки со статусом, сроком, прогрессом и обложкой, порядок «сначала новые / старые», пагинацию, локальные фильтры текущей страницы и состояния загрузки, пустого контракта и ошибки RPC. PR 6 добавил страницу кампании `/campaigns/[id]`: проверку ID из адреса, чтение кампании и личного вклада, панель сбора, правила режима, вычисление доступных действий без отправки транзакций и состояния неверного адреса, отсутствующей кампании и ошибки RPC. PR 7 добавил пожертвование: проверку суммы, симуляцию перед подписью, отправку через кошелёк, ожидание блока, перевод ошибок контракта и обновление данных после подтверждения. PR 8 добавил создание кампании `/campaigns/new`: проверку лимитов контракта в байтах UTF-8 до подписи, превью карточки и вызова `createCampaign`, общий жизненный цикл транзакции и переход на новую кампанию по ID из события `CampaignCreated`. PR 9 добавил остальные действия на странице кампании: возврат вклада, отмену, вывод средств и смену срока с переводом ошибок контракта по смыслу конкретного действия. PR 10 провёл приёмку: шапка больше не теряет кнопку кошелька на 960–1279 px, контраст цифр шагов в тёмной теме поднят до 5,28:1, поля ввода уважают reduced motion, а ссылка цепочки навигации получила цель касания 24 px. История этапов — [`archive/frontend-mvp.md`](archive/frontend-mvp.md). После завершения MVP проект перешёл к этапу backend/indexer.

Полный локальный стек запускается через Docker Compose (#46). Локальный деморежим с Anvil и двумя ролями доступен через отдельный Compose-проект (#48). Порядок запуска, настройки и восстановление базы и обложек описаны в [`docker.md`](docker.md).

Продуктовая концепция описана в [`product-vision.md`](product-vision.md), порядок этапов — в [`roadmap.md`](roadmap.md).

## Что работает в V2

- создание fixed-кампаний сроком от 1 до 365 дней и open-ended-кампаний без дедлайна;
- изменение дедлайна fixed-кампании creator до первого пожертвования;
- пожертвования в ETH и учёт личных вкладов;
- немедленный успех при достижении цели и запрет последующих пожертвований;
- отмена кампании creator до достижения цели;
- вывод средств сразу после достижения цели;
- возврат вкладов проваленной или отменённой кампании;
- активный возврат из open-ended-кампании до достижения цели;
- вычисляемые статусы кампании;
- ограниченная постраничная загрузка кампаний;
- события для всех финансовых и жизненных переходов кампании;
- deployment через Foundry и чтение состояния через `cast`.

## Следующий учебный шаг

Frontend MVP, backend/indexer и локальный деморежим реализованы. Дальнейшие задачи выбираются по [`roadmap.md`](roadmap.md) и на доске. Стек выбран: Node.js, TypeScript и Fastify, PostgreSQL с миграциями Drizzle. Модель indexer выбрана: опрос `eth_getLogs` до `finalized` блока, события, проекция и checkpoint в одной транзакции, см. [`DECISIONS.md#indexer-reads-finalized-logs`](DECISIONS.md#indexer-reads-finalized-logs). Публичный RPC frontend не хранит логи с блока deploy, поэтому indexer получает собственный RPC, см. [`gotchas.md#public-rpc-prunes-log-history`](gotchas.md#public-rpc-prunes-log-history). Вход подписью (SIWE), устройство пакета `backend/`, API, обработка обложек и тесты тоже решены, см. указатель [`DECISIONS.md`](DECISIONS.md#указатель). Решений до кода больше не осталось. Создан каркас `backend/`: Fastify с `GET /health`, проверка конфигурации при старте, плавная остановка, единый формат ошибок, ESLint с правилами по типам, 8 тестов и отдельный job CI, см. [`architecture.md#backend`](architecture.md#backend). Подключён PostgreSQL 18.4 из `compose.yaml` через пул `pg` и Drizzle, маршрут `/ready` проверяет базу, тесты и CI работают с настоящей тестовой БД. Первая миграция создала таблицы `chain_events` и `indexer_checkpoints` с ограничениями на уровне базы; `uint256` хранится как `NUMERIC(78, 0)` без потери точности. Модуль `chain` дал backend ABI с типами событий, адрес и блок deploy V2, сверенные тестами с frontend и `deployments.md`, и клиент viem из обязательной `SEPOLIA_RPC_URL`. Маршруты описываются схемами TypeBox; для входа подписью созданы таблицы `auth_nonces` и `auth_sessions` (в базе только хэш идентификатора сессии). Вход подписью (#52) готов: одноразовый nonce, проверка сообщения EIP-4361 и подписи, серверная сессия в `httpOnly`-cookie, чтение сессии и выход, хук `requireSession` для будущих маршрутов, лимиты по адресу клиента и не зависящие от него, проверка `Origin`; живой вход проверен кошельком Rabby через прокси Next.js. Текущие задачи и их порядок ведутся на доске [OpenFund Delivery](https://github.com/users/Ilja-Prihach/projects/1), процесс — в [`workflow.md`](workflow.md); стенд Anvil (#58) готов: интеграционные тесты backend разворачивают V2 на локальном узле, создают все события и проверяют вход смарт-кошельком. Frontend умеет входить подписью из меню кошелька (#59): вход, выход, завершение сессии при смене аккаунта и отключении кошелька. Indexer (#54) — отдельный процесс, читает finalized-логи пачками и хранит checkpoint. Публичный 1rpc не выдержал полной догрузки, поэтому до публикации indexer читает историю через публичный Tenderly без ключа (#89), см. [`DECISIONS.md#indexer-reads-history-from-public-tenderly`](DECISIONS.md#indexer-reads-history-from-public-tenderly); 15 ноября 2026 года вся история V2 — 25 событий — догружена до `finalized`. Indexer строит проекции кампаний и вкладов в той же транзакции, пересобирает их из журнала командой `npm run indexer:rebuild` и сверяет с контрактом; первая живая сверка совпала по всем 10 кампаниям (#53), см. [`DECISIONS.md#indexer-projections-apply-each-event-once`](DECISIONS.md#indexer-projections-apply-each-event-once). API каталога (#47) отдаёт `GET /v1/campaigns` с поиском, фильтрами по статусу и режиму, сортировкой по собранной сумме и блоком данных; статусы вычисляются по правилам контракта и при живой проверке совпали с `getCampaignStatus` по всем 10 кампаниям. Все ответы backend несут заголовки `@fastify/helmet`. Каталог frontend (#60) ищет, фильтрует и сортирует через этот API, честно показывает блок данных и при недоступном backend откатывается на чтение контракта. API отдаёт ленту событий кампании с keyset-курсором и временем блока, донатеров с историей внесённого и возвращённого и число участников в каталоге (#50); при живой проверке суммы всех донатеров совпали с `contributions()` контракта, а время всех 25 событий — с блоками Sepolia. Страница кампании показывает участников и ленту активности из этого API, а карточка каталога — число участников (#94); при недоступном backend или ещё не дочитанной кампании блоки истории объясняют причину, а суммы и действия остаются из контракта. Backend хранит детали кампании от создателя — категорию, историю, бюджет, план, риски и обложку (#49): менять их может только адрес сессии, совпадающий с `creator` кампании в контракте, обложка пережимается в WebP 1200×675 без EXIF и хранится за интерфейсом `MediaStorage` в локальной папке, каталог отдаёт категорию и обложку и фильтрует по категории; при живой проверке чужой адрес получил `403` на кампаниях Sepolia №0 и №1. Frontend показывает обложки и категории в каталоге и на странице кампании, фильтрует по категории и выводит разделы создателя с пометкой Off-chain (#98); таблица demo-обложек удалена, обложки кампаний 3–8 перенесены в backend командой оператора. Без backend каталог и страница показывают узоры. Редактор `/campaigns/:id/edit` (#62) позволяет создателю до первого пожертвования отдельно сохранить обложку, категорию, историю, бюджет, план и риски; после доната backend отвечает `409` и сохраняет блокировку после возврата по журналу событий. Следующая задача выбирается на доске.

Главная (#63) показывает статистику OpenFund V2 и до трёх последних активных кампаний из одного снимка данных Sepolia. Назначение показателей и поведение при недоступном источнике описаны в [архитектуре](architecture.md#frontend-shell-и-дизайн-система).

Backend профилей (#51) реализован: публичное чтение профиля по адресу, создание/редактирование через SIWE-сессию, списки созданных и поддержанных кампаний с пагинацией и finalizedBlock. Поддержка остаётся в истории после полного возврата. Первая версия — один кошелёк на профиль; объединение требует отдельного протокола. Frontend (#61) показывает публичную страницу `/profiles/:address`, вкладки кампаний и форму владельца; переходы доступны из меню кошелька и страницы кампании. API и модель описаны в [`architecture.md#профили-backend`](architecture.md#профили-backend).

## Известные ограничения

- абсолютную атомарность правила «до первого пожертвования» V2 дать не может: после полного возврата ещё не финализированного доната и до обработки события indexer остаётся узкое окно; текущий `totalRaised` и постоянный журнал закрывают обычные сценарии, см. [`DECISIONS.md#campaign-details-freeze-after-first-donation`](DECISIONS.md#campaign-details-freeze-after-first-donation);
- если backend недоступен, каталог откатывается на чтение контракта, и тогда фильтры действуют только на загруженную страницу, а поиск, категории и сортировка по сумме отключены, вместо обложек — узоры;
- в MetaMask со скрытыми тестовыми сетями программное переключение на Sepolia завершалось внутренней ошибкой окна расширения (`Cannot read properties of undefined (reading 'origin')`); причина не подтверждена, обход — включить тестовые сети и выбрать Sepolia вручную, о чём подсказывает полоса неверной сети;
- `npm audit` frontend чистый после обновления Next.js и транзитивного `typescript-eslint`. В backend остаются dev-only moderate-находки, не затрагивающие production: minimatch (GHSA-g3hv-75wg-m249) внутри `typescript-eslint` и esbuild 0.18 (GHSA-67mh-4wv8-2f99) внутри `drizzle-kit`; шаблоны minimatch берутся только из нашего конфига ESLint, а dev-сервер esbuild не запускается. `npm audit --omit=dev` чистый в обоих приложениях; install-скрипты esbuild в backend запрещены через `allowScripts`;
- контракт развёрнут только в тестовой сети, Mainnet deployment не планируется на текущем этапе;
- исходники подтверждены Sourcify, но отдельно через Etherscan API не верифицировались;
- актуальная Sepolia оценивает deployment gas значительно выше локальной Cancun-симуляции; перед любым следующим deployment требуется новый RPC estimate, см. [`gotchas.md`](gotchas.md#sepolia-deployment-gas-differs-from-local-simulation).

## Цель

Пользователь подписывает сообщение EIP-4361 кошельком и получает серверную сессию. Браузер хранит только случайный идентификатор в cookie, сессия отзывается удалением строки в БД. Интерфейса входа здесь нет, он делается в #59.

## Поток

```
браузер                               backend                              PostgreSQL
  │ POST /v1/auth/nonce ───────────────▶ случайный nonce ─────────────────▶ auth_nonces (+10 мин)
  │ ◀─────────────────────────── { nonce }
  │ кошелёк подписывает сообщение SIWE (без транзакции и газа)
  │ POST /v1/auth/verify { message, signature }
  │                                     разбор и проверка полей сообщения
  │                                     проверка подписи (viem, RPC для смарт-кошельков)
  │                                     одна транзакция: ─────────────────▶ DELETE nonce RETURNING
  │                                                                         INSERT auth_sessions
  │ ◀──────────── 200 + Set-Cookie: openfund_session=<случайный id>
  │ GET /v1/auth/session ──────────────▶ хэш id из cookie ────────────────▶ поиск живой сессии
  │ POST /v1/auth/logout ──────────────▶ DELETE сессии, очистка cookie
```

## Что выяснено до кода

Проверено чтением исходников viem `2.57.13` в `backend/node_modules/viem/_esm/`.

1. **`generateSiweNonce()` из viem брать нельзя.** Он строит nonce из `Math.random()` и выдаёт подстроки одного буфера со сдвигом на один символ. Воспроизведено: у двух nonce подряд `b.slice(0, 95) === a.slice(1)` → `true`, то есть один увиденный nonce почти целиком раскрывает следующий. Nonce будем делать сами через `crypto.randomBytes` из Node.js. Эта находка станет карточкой в `gotchas.md`.
2. **`verifySiweMessage` проверяет не всё.** Внутри `validateSiweMessage` сверяются только `domain`, `nonce`, `scheme`, адрес, `expirationTime` и `notBefore`. **Не** проверяются `chainId`, `uri`, `version` и свежесть `issuedAt`. Их backend проверяет сам: разбирает сообщение через `parseSiweMessage`, и только потом вызывает проверку подписи.
3. **Подпись даже обычного кошелька сначала проверяется через RPC.** В режиме по умолчанию `verifyHash` делает `eth_call` к валидатору ERC-6492. Если вызов падает, viem пробует восстановить адрес из подписи локально (`recoverAddress`). Следствия:
   - вход — первый потребитель `createChainClient` из #57, клиент передаётся в `buildApp` зависимостью;
   - при недоступном RPC обычные кошельки входят через локальную проверку, а смарт-кошельки — нет;
   - в тестах клиент подменяется транспортом, который не ходит в сеть.

## Таблицы

`auth_nonces`:

| Колонка | Тип | Смысл |
| --- | --- | --- |
| `nonce` | `text`, PK | 32 случайных байта в hex; `CHECK` на формат |
| `expires_at` | `timestamptz` | выдача + 10 минут |

`auth_sessions`:

| Колонка | Тип | Смысл |
| --- | --- | --- |
| `id_hash` | `text`, PK | SHA-256 идентификатора из cookie, а не сам идентификатор |
| `address` | `text` | адрес кошелька в нижнем регистре, `CHECK` как в `chain_events` |
| `created_at` | `timestamptz` | момент входа |
| `expires_at` | `timestamptz` | вход + 7 дней, без продления |

В БД лежит только хэш идентификатора сессии. Утечка дампа базы не даёт готовых cookie: по хэшу нельзя восстановить значение. Просроченные строки чистятся попутно при выдаче nonce и при входе; отдельного планировщика нет.

## Правила проверки `POST /v1/auth/verify`

1. Тело по схеме TypeBox: `message` — строка до 2 000 символов, `signature` — hex.
2. `parseSiweMessage`. Затем сверяются:
   - `domain` и `uri` — с источником frontend из `APP_ORIGIN`;
   - `chainId` = `11155111`;
   - `version` = `"1"`;
   - `issuedAt` не в будущем (допуск 1 минута) и не старше 10 минут;
   - `expirationTime` и `notBefore`, если они есть.
3. `verifySiweMessage` проверяет подпись.
4. Одна транзакция:
   - `DELETE FROM auth_nonces WHERE nonce = $1 AND expires_at > now() RETURNING`;
   - если строки нет, вход отклоняется;
   - иначе `INSERT` сессии.

   Два параллельных запроса с одной подписью не могут оба удалить nonce, поэтому повтор подписи отклоняется даже в гонке.
5. Ответ `200 { address, expiresAt }` и cookie `openfund_session`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age` 7 дней.

Любая ошибка проверки отвечает `401` с единым кодом `SIWE_INVALID`. Клиенту не важно, что именно не сошлось, а подробности упрощали бы подбор. Причина пишется в лог уровня `info` без текста сообщения и подписи. Ошибка RPC при проверке смарт-кошелька отвечает `503`.

## Защита

- **Rate limit:** `@fastify/rate-limit` только на `/v1/auth/*`, примерно 10 запросов в минуту с IP на маршрут. Точные числа зададим в шаге 6.
- **CSRF:** cookie `SameSite=Lax` не уходит с POST-запросами чужих сайтов. Дополнительно POST-маршруты входа сверяют заголовок `Origin` с `APP_ORIGIN`.
- **Логи:** по умолчанию Fastify не пишет заголовки и тела запросов. Сверх этого `redact` вырезает `cookie` и `set-cookie`, а тест перехватывает поток логов и проверяет, что в нём нет cookie, подписи и сообщения SIWE.
- **Новая обязательная переменная `APP_ORIGIN`:** источник frontend, например `http://localhost:3000`. Из неё берутся ожидаемые `domain` и `uri` сообщения.

## Адрес клиента и лимиты

Лимит по IP работает, только если backend знает настоящий адрес браузера. За прокси backend видит адрес прокси, а настоящий адрес приходит в заголовке `X-Forwarded-For`, который может прислать и сам клиент.

- **Прокси Next.js заголовок не защищает.** В `next` 16.4.3 `base-server.js` выставляет `x-forwarded-for` через `??=`, только если заголовка ещё нет, а прокси `httpxy` запущен без `xfwd`. Присланный клиентом заголовок проходит без изменений. Вывод сделан по коду; живая проверка — в #77.
- **В продакшене один источник даёт внешний reverse proxy**, который перезаписывает `X-Forwarded-For` адресом соединения (#64).
- **Backend доверяет заголовку только от известного прокси.** `TRUST_PROXY` (адреса или CIDR, по умолчанию пусто) передаётся в Fastify `trustProxy`: адрес клиента — первый справа в `X-Forwarded-For`, не принадлежащий доверенному прокси.
- **Лимиты, не зависящие от IP.** Потолок живых nonce (сверх него `503`) защищает таблицу, а общий лимит `verify` в минуту — квоту RPC: каждая проверка делает `eth_call`. Даже ошибка в определении адреса не уронит базу и не сожжёт квоту.

## Шаги

Каждый шаг идёт в учебном формате: сначала теория и точный код, потом «ок», потом применение и вопросы на понимание. Каждый шаг заканчивается зелёными `lint`, `typecheck` и `test`.

1. **TypeBox.**
   - type provider в `buildApp`, схемы ответов `/health` и `/ready`, `ApiError` из схемы;
   - доказательство: неверный ответ обработчика ломает `npm run typecheck`.
2. **Схема.**
   - таблицы `auth_nonces` и `auth_sessions`, миграция `auth_nonces_and_sessions`;
   - тесты `CHECK` и первичных ключей на настоящем PostgreSQL.
3. **Nonce.**
   - `APP_ORIGIN` в `loadEnv`, клиент цепочки в зависимостях `buildApp`, префикс `/v1/auth`: всё это появляется вместе с первым маршрутом, который его использует;
   - `POST /v1/auth/nonce`, nonce из `crypto.randomBytes`, срок 10 минут, попутная чистка просроченных;
   - тесты: формат, уникальность, запись в БД.
4. **Проверка подписи.**
   - `POST /v1/auth/verify` по правилам выше;
   - тесты на настоящих подписях одноразовых ключей `privateKeyToAccount`. Негативные сценарии:
     - чужой domain, uri, chainId, version;
     - просроченный и будущий `issuedAt`;
     - неизвестный, просроченный и уже использованный nonce;
     - подпись другого адреса, испорченная подпись;
     - гонка двух запросов с одной подписью.
5. **Сессия и выход.**
   - `GET /v1/auth/session`, `POST /v1/auth/logout`;
   - общий хук `requireSession` для будущих маршрутов #49 и #51;
   - тесты: просроченная сессия, сессия после выхода, подделанная cookie.
6. **Защита и документация.**
   - rate limit, `TRUST_PROXY` и тест подделанного `X-Forwarded-For`, потолок nonce и общий лимит `verify`, проверка `Origin`, `redact` в логгере и тест логов;
   - `security.md`, `architecture.md`, `backend/README.md`, карточка gotcha про nonce viem;
   - живая проверка входа с настоящим кошельком через `curl` и подпись в Rabby.
